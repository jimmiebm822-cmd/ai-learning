各域详细诊断

1. Agent 架构基础 — ✅ 已掌握

你已掌握：Loop Engineering 五步框架（Discovery→Handoff→Verification→Persistence→Scheduling）、六大模式（Classify-and-act、Fan-out、Adversarial Verification、Generate-and-filter、Tournament、Loop until done）、三大失败模式（Agentic laziness、Self-preferential bias、Goal drift）。

需补强：这些知识来自实践和 Anthropic blog 蒸馏，但缺乏学术形式化。建议阅读 Lilian Weng 的 LLM Powered Autonomous Agents（仍是 canonical reference）建立 Planning + Memory + Tool Use 三组件框架，再读 arXiv 2606.20683 "From Question Answering to Task Completion" 了解 model-harness decoupling 理论。

2. Context Engineering — ❌ CRITICAL

为什么 CRITICAL：Anthropic 2025-09 发表 "Effective Context Engineering for AI Agents"，明确提出 context engineering > prompt engineering 的范式迁移。这不是换了个词 — 它意味着你的思维模型需要从"写好 prompt"变成"管理一个有限的 token 预算，在运行时动态加载和驱逐信息"。

你缺的具体知识：

  • Just-in-time context：不预加载所有数据，维护轻量标识符（文件路径、查询、链接），运行时动态加载 — Claude Code 就是这么做的
  • Context as finite resource：Agent 在 loop 中生成指数增长的数据，必须循环精炼 — 你的 loop-engineering 有这个直觉但缺形式化
  • Mirrors human cognition：人不记忆整个语料库 — 用文件系统、收件箱、书签。Agent 也应该这样
  • Progressive disclosure：Anthropic Agent Skills 的三级加载（metadata → SKILL.md → bundled files）— 你的 Hermes skills 就是这个模式但你可能不知道理论框架

学习材料：Anthropic — Effective Context Engineering + Agent Skills 开放标准

3. Tool Design & MCP — ❌ CRITICAL

为什么 CRITICAL：Tools 是确定系统与非确定 agent 之间的契约。MCP (Model Context Protocol, Anthropic 2024-11) 已成为事实标准。你的 Hermes 有 tools 但没系统学过 tool design 原则。

你缺的具体知识：

  • Tool 作为新型软件：agent 可能调用 tool、用通用知识回答、或追问 — tool 必须为 agent 设计而非为开发者设计
  • Token 开销问题：5 个 MCP server (58 个 tools) = ~55K tokens 开销 — 必须按需加载
  • Programmatic Tool Calling：agent 写代码调用 tool（而非直接调用），中间结果留在代码执行环境 — 不进 context window
  • Tool Use Examples：JSON schema 无法表达使用模式（何时带可选参数、哪些组合有意义）— 需要示例
  • MCP 安全风险：Tool poisoning、tool shadowing、rug pulls — Simon Willison 已有多篇分析

学习材料：Writing Effective Tools for Agents + Advanced Tool Use + Code Execution with MCP

4. Agent Evaluation — ❌ CRITICAL

为什么 CRITICAL：你有 adversarial verification rubric，但这不等于 agent evaluation。Agent evals 和 single-turn evals 是根本不同的 — mistakes 会传播和复合。没有系统 evals，你只能 reactive 地发现问题（用户报告 bug），而不是 proactive 地在上线前发现。

你缺的具体知识：

  • 核心定义：Task（单次测试）→ Trial（多次尝试求一致性）→ Grader（评分逻辑）→ Transcript（完整轨迹记录）
  • Trajectory diagnostics：不只看 pass/fail — 分析 agent 的搜索、读取、编辑、工具调用、验证、回退轨迹（arXiv 2607.06184 的 9 类 action taxonomy）
  • Optimizer-Evaluator 分离："An optimizer that grades itself learns to game the metric" — Google 的 flywheel 和你的 adversarial verification 不谋而合
  • Benchmarks 全景：SWE-bench（代码）、GAIA（通用）、UniClawBench（400 真实任务）、DeepSWE（113 无污染任务）
  • Eval contamination：模型能识别自己在被测试（Opus 4.6 在 BrowseComp 上发现了答案并解密）— benchmark 可能不可靠

学习材料：Demystifying Evals for AI Agents + arXiv 2607.05775 "Beyond the Leaderboard" + arXiv 2607.06184 "Trajectory Diagnostics"

5. Harness Engineering — 🔄 PARTIAL

你已掌握：Harness 是 loop 的第四层（prompt → context → harness → loop），来自 Anthropic "A Harness for Every Task"。

你缺的具体知识：

  • 三层虚拟化抽象：Session（追加日志，outlasts 任何 context window）≠ Harness（调用 Claude + 路由 tool calls 的 loop）≠ Sandbox（执行环境）
  • "Don't adopt a pet"：初始所有组件在单容器（"pet" — 手工维护、不可丢失）→ 重构为 "cattle"（可互换、brain 与 hands 解耦）
  • Context anxiety：模型接近 context 上限时提前结束工作 — 需要 context resets（清理 context window），但要小心操作
  • GAN-inspired 评估：Generator agent 产出 + Evaluator agent 评分 — 把主观判断（"设计好不好"）变成可评分的
  • Long-running agents：Initializer agent（首次设置环境）+ Coding agent（每次增量推进，留 artifact 给下次）

学习材料：Effective Harnesses for Long-Running Agents + Scaling Managed Agents + Harness Design for Long-Running Apps

6. Agent Memory Systems — 🔄 PARTIAL

你已掌握：Obsidian Vault + LLM Wiki 的记忆管线 v3.0，structured-memory-system 已删除并入 Obsidian。

你缺的学术框架：

  • Rate-distortion 统一框架：arXiv 2607.08032 — 把 KV cache eviction、prompt pruning、architectural state bounding、agent memory consolidation 四个社区统一到同一个 retain/discard 决策问题
  • Self-optimizing memory：arXiv 2607.03726 (SelfMem) — agent 学习自己的 memory strategy，而非预定义
  • Behavioral state decay：arXiv 2607.08716 — 长程任务中决策相关状态散落在不断增长的轨迹中，被推出 context window 后不再影响决策
  • Hierarchical memory：arXiv 2607.07666 — 三层架构保持 context bounded（中位 301 tokens，max 4050 across 104 runs）
  • Neural procedural memory：arXiv 2606.29824 — 从 RAG（显式文本注入）到 activation-based（隐式激活引导）的转变

7. Agent Safety & Security — 🔄 PARTIAL

你已掌握：agent-defense-prompt skill（嵌入式 defense prompt，6,000+ 攻击 0 成功）、Cron injection 扫描器误杀的坑。

你缺的全景：

  • Lethal Trifecta（Willison）：private data + untrusted content + external communication = dangerous。三者同时存在 = 系统性风险
  • Rule of Two（Meta AI）：每个 session 最多拥有 2/3 个危险属性。受 Chrome Rule of 2 启发
  • Decomposition attacks：有害任务拆成看起来无害的子任务 — 单独执行通过安全检查，累积完成恶意意图（arXiv 2606.13994 DECOMPBENCH）
  • Memory poisoning：arXiv 2607.06595 — 长期记忆成为攻击面，攻击者注入虚假记忆影响后续决策
  • Dual-boundary security：arXiv 2606.09549 (SecureClaw) — effect sink（action authorization）+ read boundary（plaintext confinement），不能只守一个
  • 247 篇安全论文综合：arXiv 2606.10749 — agent 安全从 text safety 进化为 agentic-specific risks（control flow hijack、tool privilege misuse、state corruption）

学习材料：Lethal Trifecta + Design Patterns for Securing LLM Agents

六大跨领域主题：2025-2026 行业共识

三路搜索（官方博客 + arXiv + 行业领袖）收敛出的六个共识，每个都是 Daddy 当前知识体系的补强方向。

① Agent = LLM + Tools + Instructions, running in a loop

Anthropic、OpenAI、Google 三家独立得出同一公式：Agent ≠ 更聪明的 LLM，而是 LLM 在 loop 中使用 tools 完成任务。开放问题是编排方式 — 单 agent + many tools vs multi-agent + handoffs。OpenAI 建议"先最大化单 agent 能力再考虑 multi-agent"，Google 推 graph-based orchestration，Anthropic 偏好 subagent fan-out。

② Context Engineering 是新的 Prompt Engineering

Anthropic 2025-09 明确提出。核心洞察：context window 是有限资源，不是"越大越好"。Agent 在 loop 中生成指数增长的数据，必须循环精炼。Just-in-time context（维护轻量标识符，运行时动态加载）是 Claude Code 的核心设计。你的 Hermes skills 的 progressive disclosure 三级加载已经暗合了这个原则，但需要系统理解理论框架。

③ Tool Design 是新的 API Design

Tools 是确定系统与非确定 agent 之间的契约。MCP 已成为事实标准（数千个 MCP server、全语言 SDK）。关键挑战：58 个 tools = 55K tokens 开销 → 需要按需加载 + Programmatic Tool Calling（agent 写代码调 tool）。Tool 质量和可发现性是扩展瓶颈。Anthropic 用 agents 优化自己的 tool descriptions — 你也可以这样做。

④ Evaluation 是最难的题

Agent evals 和 single-turn evals 是根本不同的：multi-turn state propagation、creative solutions that surpass static criteria、eval contamination（模型能找到 web 上的 benchmark 答案）。核心原则："An optimizer that grades itself learns to game the metric" — optimizer 和 evaluator 必须解耦。Google 的 Agent Quality Flywheel（Build Test → Ship Monitor → Learn Refine）和你的 adversarial verification 不谋而合。

⑤ 从 Static Deployment 到 Self-Evolving Agents

多个 arXiv 论文指向同一结论：下一代范式是持续从自身经验学习的 agent。MetaSkill-Evolve (2607.05297) 实现递归自改进（meta-skill 也在进化）。Failure-driven self-improvement (2606.31270) 从失败轨迹提取可行动信号。Self-evolving RL systems (2607.01120) 提出生产环境中的自进化框架。你已有 self-evolving-loop-research 的 references，但需要补齐学术框架。

⑥ Agent 安全是多边界防御，无银弹

三个独立安全框架收敛：Lethal Trifecta (Willison)、Rule of Two (Meta)、Six Design Patterns (IBM/Google/Microsoft paper)。核心共识：通用 agent 无法提供可靠安全保证 — 必须通过限制 agent 能力来换取安全。Memory 已成为新攻击面（memory poisoning）。Decomposition attacks 绕过单步安全检查。Dual-boundary security（effect sink + read boundary）是学术前沿。
