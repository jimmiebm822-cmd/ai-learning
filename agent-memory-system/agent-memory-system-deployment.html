10|

11|## 1. 为什么需要这个系统

12|

13|LLM Agent 的核心限制：context window 是有限的。每次会话开始，Agent 没有上一次的任何记忆。传统解决方案是 RAG — 但 RAG 在每次查询时从原始文档重新发现知识，不累积结构、不标记矛盾、不建交叉引用。

14|

15|LLM Wiki Pattern（来自 Karpathy）反过来：编译一次，编译出的 wiki 持续维护、累积结构、累积交叉引用、累积已标记的矛盾。

16|

17|```

18|raw 源 → [LLM 编译] → interlinked .md wiki → [LLM Q&A / lint] → 持续增值

19|```

20|

21|| 维度 | RAG | LLM Wiki |

22||------|-----|----------|

23|| 知识组织 | 查询时重组 | 预先编译，持续累积 |

24|| 交叉引用 | 查询时发现 | 已内建 [[wikilinks]] |

25|| 矛盾处理 | 可能重复呈现矛盾 | 已标记，供 review |

26|| 综合质量 | 每次重新综合 | 反映已 ingest 的全部内容 |

80|## 3. LLM Wiki 部署

81|

82|### 3.1 目录结构

83|

84|```

85|LLM Wiki/

86|├── SCHEMA.md ← 结构约定 + tag taxonomy（Agent 每次会话先读）

87|├── index.md ← 内容目录（每页附一行摘要）

88|├── log.md ← 操作日志（每个写操作追加一行）

89|├── _meta/ ← 元数据（lint 报告等）

90|├── concepts/ ← 概念页（方法论、模式、框架）

91|├── entities/ ← 实体页（工具、平台、模型）

92|├── comparisons/ ← 对比页（A vs B 选型）

93|├── queries/ ← 查询结果页（复杂问题的编译答案）

94|└── raw/ ← 不可变原始素材

95| ├── articles/ ← 文章原文

96| ├── papers/ ← 论文原文

97| ├── transcripts/ ← 对话/播客 transcript

98| └── assets/ ← 图片等

99|```

100|

101|### 3.2 SCHEMA.md — 结构约定

102|

103|SCHEMA.md 是整个系统的"宪法"。Agent 在每次会话开始必须先读这个文件。它定义：

104|

105|文件命名规则：

106|- 英文、小写、连字符，无空格（如 agent-orchestration.md）

107|- 中文概念用英文 slug，正文可中文

108|

109|页面长度限制：

110|- 每页上限 60 行（确保可独立加载、精准路由）

111|- 超过 60 行 → 按子主题"有机拆解"为子页面（不是机械切割）

112|- 子页面在父页面的 frontmatter 中用 sub_pages 列出

113|

114|YAML Frontmatter 格式：

115|

116|```yaml

117|---

118|title: Page Title

119|created: YYYY-MM-DD

120|updated: YYYY-MM-DD

121|type: entity | concept | comparison | query | summary

122|tags: [from taxonomy]

123|sources: [raw/articles/source-name.md]

124|# 子页面集合的父页面使用：

125|sub_pages: [sub-slug-1, sub-slug-2]

126|# 可选质量信号：

127|confidence: high | medium | low

128|contested: true

129|contradictions: [other-page-slug]

130|---

131|

132|# 页面标题

133|

134|> 一句话摘要（做什么用的）

135|

136|## 正文内容

137|

138|每页至少 2 个 [[wikilinks]] 出站链接。

139|

140|^[raw/articles/source-file.md] ← provenance 标记

141|```

142|

143|raw/ 子目录的 Frontmatter：

144|

145|```yaml

146|---

147|source_url: https://example.com/article

148|ingested: YYYY-MM-DD

149|sha256:

150|---

151|```

152|

153|sha256 让未来重新 ingest 同一 URL 时检测内容漂移（相同→跳过，不同→标记）。

154|

155|### 3.3 Tag Taxonomy（必须先定义再用）

156|

157|SCHEMA.md 中定义的 tag 表是封闭的 — 页面上的每个 tag 必须出现在 taxonomy 表中。新增 tag 先加到 SCHEMA.md 再用。

158|

159|建议的分类维度（根据你的领域调整）：

160|

161|```

162|Models: model, llm, inference, context-engineering

163|Platforms: hermes, obsidian, wsl, claude-code, codex

164|Practices: vibe-coding, agent-orchestration, debugging, automation, cron

165|Domain: (你的业务领域 tag)

166|```

167|

168|### 3.4 核心工作流

169|

170|Ingest（知识摄入）：

171|1. 原始素材放入 raw/articles/ 或 raw/papers/

172|2. Agent 读 SCHEMA.md → 读 index.md → 读 log.md（最近 30 行）

173|3. Agent 提炼知识到 wiki 页面，建 [[wikilinks]] 交叉引用

174|4. 更新 index.md 添加新页面条目

175|5. 追加 log.md 记录操作

176|

177|Q&A（知识查询）：

178|1. Agent 读 SCHEMA.md → 读 index.md 定位相关页面

179|2. 读具体页面回答问题

180|3. 有价值的答案"filing"回 wiki（更新已有页面或创建新页面）

181|

182|Lint（健康检查）：

183|- 找 orphan 页（无入站链接）

184|- 找断链（[[wikilink]] 指向不存在的页面）

185|- 找 frontmatter 缺失的页面

186|- 找 stale 内容（updated 日期过旧）

187|- 找矛盾标记（contested: true）

192|

193|### 4.1 日志格式

194|

195|每日日志文件命名：YYYY-MM-DD.md，存放在 Obsidian Vault 的 每日日志/ 目录。

196|

197|```yaml

198|---

199|created: 2026-07-12

200|tags: [daily-log, memory-index]

201|type: daily

202|---

203|

204|# 2026-07-12 记忆索引

205|

206|> 本日志仅包含具有长期价值的记忆。事务性内容已过滤。

207|

208|## 技术决策

209|

210|- 决策标题：决策内容描述。涉及 [[related-wiki-page]]。

211|

212|## 方法论突破

213|

214|- 方法论标题：方法论描述。

215|

216|## 知识积累

217|

218|- 知识标题：知识描述。详见 [[related-wiki-page]]。

219|

220|---

221|> 📚 待 wiki-sync 拆解：

222|> - [[page-name]] → 拆解方向说明

223|```

224|

225|### 4.2 内容过滤规则

226|

227|❌ 直接丢弃的内容：

228|- Cron 运行元数据（跑了多少次、有无新邮件、运行时间）

229|- 日常事务性操作（启动了某个服务、打开了某个 session）

230|- 邮件摘要内容（属于邮件系统，不属于长期记忆）

231|- 纯执行性操作没有长期价值的

232|

233|✅ 需要捕捉的内容：

234|

235|| 类别 | 判断标准 | 示例 |

236||------|---------|------|

237|| 技术决策 | 涉及架构选择、方向判断、trade-off 分析 | "决定用模块化分解而非单体架构" |

238|| 方法论突破 | 新发现的方法、模式、改进 | "三路并行搜索+综合产出工作流" |

239|| 系统异常 | 涉及系统性问题（非偶发） | "跨 profile 协作发现隔离问题" |

240|| 知识积累 | 新学到的、可复用的知识 | "Context Engineering 是 prompt eng 的范式迁移" |

241|

242|### 4.3 设计原则

243|

244|1. 不是流水账 — 目标是产出简洁但有深度的记忆索引，供明天的 wiki-sync 拆解和路由

245|2. 每条必须可路由 — 每条记忆要能对应到一个 wiki 页面（已有或待创建）

246|3. 底部待拆解区 — 日志末尾标注"待 wiki-sync 拆解"的清单，指导下一步同步

251|

252|### 5.1 Cron 1: 记忆索引（每日 22:00）

253|

254|目标：扫描今天的对话，提取具有长期价值的内容，写入 Obsidian 每日日志。

255|

256|Cron 配置：

257|```json

258|{

259| "id": "memory-index-cron",

260| "name": "Obsidian 记忆索引",

261| "schedule": { "kind": "cron", "expr": "0 22 * * *" },

262| "skills": ["obsidian"],

263| "enabled_toolsets": ["terminal", "file", "session_search"]

264|}

265|```

266|

267|Agent Prompt 核心：

268|```

269|你是长期记忆 curator。扫描今天的对话，提取具有长期价值的内容，写入 Obsidian 每日日志。

270|这不是流水账。目标是产出简洁但有深度的记忆索引，供明天的 wiki-sync 管线逐条拆解和路由。

271|

272|## 内容过滤规则

273|

274|### ❌ 直接丢弃：

275|- cron 运行元数据

276|- 纯事务性操作

277|- 邮件摘要内容

278|

279|### ✅ 需要捕捉：

280|| 类别 | 判断标准 |

281||------|---------|

282|| 技术决策 | 涉及架构选择、方向判断、trade-off |

283|| 方法论突破 | 新发现的方法、模式、改进 |

284|| 系统异常 | 涉及系统性问题（非偶发） |

285|| 知识积累 | 新学到的、可复用的知识 |

286|

287|## 输出格式

288|写入 /path/to/Obsidian Vault/每日日志/{今天日期}.md

289|按 4 个分区组织：技术决策 / 方法论突破 / 系统异常 / 知识积累

290|末尾加"待 wiki-sync 拆解"清单。

291|```

292|

293|### 5.2 Cron 2: Wiki 模块化同步（每日 12:00）

294|

295|目标：读昨天的每日日志，逐条拆解，增量注入 Wiki 已有页面（不创建"日记"页）。

296|

297|Cron 配置：

298|```json

299|{

300| "id": "wiki-sync-cron",

301| "name": "Obsidian→Wiki 模块化同步",

302| "schedule": { "kind": "cron", "expr": "0 12 * * *" },

303| "skills": ["obsidian-wiki-sync", "obsidian", "llm-wiki"]

304|}

305|```

306|

307|Agent Prompt 核心：

308|```

309|执行 Obsidian 记忆索引 → LLM Wiki 模块化同步。

310|

311|## 核心原则

312|不创建"日记"页。不整篇搬运。 把昨天的记忆索引逐条拆解，增量注入 Wiki 已有页面。

313|

314|## Step 1: 定位源文件

315|读 /path/to/Obsidian Vault/每日日志/{昨天日期}.md

316|

317|## Step 2: 读取 Wiki 现状

318|读以下文件作为路由上下文：

319|- /path/to/LLM Wiki/index.md — 已有页面目录

320|- /path/to/LLM Wiki/SCHEMA.md — 约定和规则

321|- /path/to/LLM Wiki/log.md（最近 30 行）— 近期活动

322|

323|## Step 3: 模块化拆解

324|逐条读取记忆索引中的每个项目。

325|

326|对每条内容执行判断：

327|| 内容特征 | 动作 |

328||---------|------|

329|| 涉及已有 concept 页的主题 | 搜索 index.md 匹配页面 → 增量更新 |

330|| 涉及已有 entity 页的主题 | 同上 → 增量更新 |

331|| 全新概念且符合创建阈值 | 按 SCHEMA.md 规范创建新页面 |

332|| 纯事务性/过时信息 | 跳过 |

333|

334|## Step 4: 更新索引和日志

335|- 更新 index.md 添加新页面条目

336|- 追加 log.md 记录所有操作

337|- 每个更新过的页面更新 updated 日期

338|```

339|

340|### 5.3 Cron 3: Meta-Verifier（每日 23:00）

341|

342|目标：跨管线的元验证 — 聚合失败模式、趋势分析、信任分更新。

343|

344|Cron 配置：

345|```json

346|{

347| "id": "meta-verifier-cron",

348| "name": "Meta-Verifier (每日 23:00)",

349| "schedule": { "kind": "cron", "expr": "0 23 * * *" },

350| "skills": ["meta-verifier"],

351| "enabled_toolsets": ["terminal", "file", "skills"]

352|}

353|```

354|

355|Agent Prompt 核心：

356|```

357|你是 Meta-Verifier — 跨管线的元验证 agent。

358|

359|## Step 1: 收集验证报告

360|从 reports/ 目录读取所有 verification_report_*.json。筛选最近 7 天。

361|

362|## Step 2: 失败模式聚合

363|按四个维度聚合：failure_category / check / data_source_ref / pipeline

364|

365|## Step 3: 趋势分析

366|对比 7 日均值 vs 前 7 日均值，判断趋势：improving / stable / worsening

367|

368|## Step 4: 跨管线关联

369|检查不同管线的 issues 是否共享 data_source_ref

370|

371|## Step 5: 新失败模式发现

372|对比已知 failure_patterns.json，发现新出现的 check+failure_category 组合

373|

374|## Step 6: 信任分更新

375|读 trust_scores.json，按规则更新每个 verifier_id 的信任分

376|

377|## Step 7: 生成 insight

378|输出 top 3 anomalies（按 severity 排序）

379|```

383|## 6. 关键设计原则

384|

385|### 6.1 编译一次，持续增值

386|传统 RAG 在每次查询时从原始文档重新发现知识。LLM Wiki Pattern 反过来：编译一次，持续维护。优势在于交叉引用和矛盾标记是累积的。

387|

388|### 6.2 模块化分解（不整篇搬运）

389|每日日志的每条记忆，按主题拆解到对应的 wiki 页面。不创建"日记"页，不整篇搬运。这确保每个 wiki 页面聚焦一个主题，可独立加载。

390|

391|### 6.3 增量注入（更新已有页面）

392|新知识优先注入已有页面（增量更新 updated 日期），只在"全新概念且符合创建阈值"时才创建新页面。这防止 wiki 膨胀。

393|

394|### 6.4 Progressive Disclosure（渐进式加载）

395|- Agent 会话开始：只加载 SCHEMA.md + index.md（几十行）

396|- 定位到相关页面后：加载具体页面（≤60 行）

397|- 需要原始素材时：从 raw/ 按需加载

398|- 这与 Anthropic 的 Context Engineering 原则完全一致

399|

400|### 6.5 Provenance Tracking

401|每个 wiki 页面在 frontmatter 中标注 sources，页面末尾用 ^[raw/articles/source.md] 标注来源。raw/ 中的文件计算 sha256，让未来重新 ingest 时检测内容漂移。

402|

403|### 6.6 闭环验证

404|22:00 记忆索引 → 12:00 Wiki 同步 → 23:00 Meta-Verifier。三个 cron 形成闭环：产出 → 消化 → 验证。Meta-Verifier 确保管线质量持续提升。

446|## 8. Pitfalls（踩坑记录）

447|
