1. 执行摘要：三缺口 + 核心论断

loop-engineering v0.3.1 的五步骤（Discovery → Handoff → Verification → Persistence → Scheduling）+ 六大模式在验证层已成熟（Adversarial Verification 是核心），但三个缺口制约其从"任务内验证循环"外推到"dynamic planning + 长时自治"：

#缺口现状目标
1Discovery 静态Classify-and-act 一次性路由，执行中不 re-plan动态重规划（外部反馈触发）
2Handoff 扁平Fan-out-and-synthesize 拆 N 份并行，无层次/依赖/动态调整层次化（递归拆解 + 依赖图）
3Scheduling 同步Loop-until-done 受单 session 上下文限制，无 checkpoint/resume长时自治 runtime

已有 v0.4 方向（Meta-Verifier / Adaptive Rubric / Insight Feed）聚焦验证层进化，与三缺口正交——本研究扩展到规划层 / 拆解层 / 执行层。

核心论断 纯 LLM 自评的自纠正几乎不奏效（Kamoi et al., TACL 2024）。真正有效的重规划都依赖外部反馈（环境 / 工具 / 验证器）作为触发信号。三个缺口的共同主题是把 loop 从"单次任务内验证循环"外推到"跨任务 / 跨会话 / 长时的 dynamic planning 闭环"——而 Hermes 已有的 Adversarial Verification 步骤正是天然的外部 critic 信号源。

2. 缺口 1：Discovery 从静态 → 动态重规划

2.1 现状

Discovery = Classify-and-act（分类 → 路由，kanban 分类卡片 + profile 分派）。一次性路由，执行中即使发现走错路也不重新分类。已验证于 SKILL.md L73。

2.2 Meta-Finding ⭐

纯 LLM 自评的自纠正几乎不奏效（Kamoi et al., TACL 2024）。真正有效的重规划都依赖外部反馈（环境 / 工具 / 验证器）作为触发信号。

→ Hermes 已有 Verification（Adversarial Verification）步骤 = 天然外部 critic 信号源。

2.4 三条核心设计启示

  1. 重规划触发信号必须来自外部 → Discovery → 执行 → Verification 评分 → 若低于阈值则重 Discovery。零新基础设施，最高 ROI。
  2. 失败应触发"重新分解"而非"简单重试"（ADaPT，+27~33% 成功率）→ Loop-until-done 升级为"失败 → 递归分解 → 重新 Discovery"。
  3. 重规划需有安全边界 → 不可信环境固化为程序；按 ToolMaze 四分类 + SERF 错误码分级处理。
未被覆盖的空白 重规划的成本 / 延迟预算控制（何时停止避免无限循环）→ Scheduling 步骤承载。重规划与任务类别分类层的耦合（文献无直接对应，Hermes 独特位置）。

3. 缺口 2：Fan-out 从扁平 → 层次化

3.1 现状

Handoff = Fan-out / Tournament（拆 N 份 → 并行 → 合成，delegate_task batch 原生支持）。扁平一次性拆解，无层次 / 依赖 / 动态调整。已验证于 SKILL.md L74。

3.2 Meta-Finding ⭐

LLM 单独规划成功率仅约 3%（LLM Planning Benchmark）→ Fan-out 不能纯靠 LLM 一次性拆解。大多数方案是两层（planner → executor），真正递归拆解的极少。

4.1 现状

Scheduling = Loop Until Done。delegate_task 同步阻塞，受单 session 上下文限制，无 checkpoint / resume。已验证于 SKILL.md L77。

4.3 关键实战案例 ⭐

long-running-coding-loop — 全自治 implement-test-fix 循环，12 小时连续运行，11/11 功能完成，$181 成本，0 人工干预。四阶段：PLAN → IMPLEMENT → COMPILE → TEST → FAIL 则 FIX。多角色分离（planner / implementer / tester 各在独立 context）。

→ 这是 Hermes Loop-until-done 的直接实战验证。

4.4 推荐的 Hermes Async Delegate 架构

delegate_task(task_spec) → AsyncDelegate
  ├─ CheckpointManager（SQLite/文件，每 step 序列化）
  ├─ ContextManager（working/recall/archival 三层 + auto-compact）
  ├─ ExecutionGuard（hooks/limits/steering/auto-mode classifier）
  └─ VerificationLoop（planner→implementer→tester，loop until pass）
       └─ callback → 主 Agent（非阻塞通知）
关键设计决策 (1) 不引入完整 Temporal server（太重）→ Hermes 内部轻量 checkpoint + retry。(2) 借鉴 Claude Code harness 模式（auto-compaction + checkpoint + subagent isolation + auto mode）。(3) MemGPT 三层 memory 作为 context 管理框架。(4) long-running-coding-loop 多角色分离作为 verification loop 模板。(5) Strands hooks + steering 作为执行可控性基础设施。

5. Claude Code Harness 四支柱

Anthropic 的 agent 方法论本质是 "简单可组合模式 + 受控 autonomy"：把 agent 定义为"LLM 在环境反馈循环里使用工具"，Claude Code 把这套理念工程化为一个 harness——由四大支柱组成的运行时外壳。🟢 官方

5.1 四支柱速查

支柱机制核心工程价值
A. Auto-Compaction context 接近 limit 时自动 summarize 成结构化摘要；CLAUDE_AUTOCOMPACT_PCT_OVERRIDE 控制触发百分比；摘要继承 extended thinking 配置 保留表：磁盘可重注入（rules/memory/skills）vs message-only 会丢（path-scoped rules / 子目录 rules）的二元分类
B. Checkpoint / Rewind 每个 user prompt 创建一个 checkpoint；自动捕获每次 edit 前的代码状态；跨 session 持久（30 天清理） 四档 rewind：回代码+对话 / 回对话 / 回代码 / 定向摘要；bash 副作用（rm/mv/cp/git reset）不可逆
C. Subagent Isolation 每个子 agent 跑在独立 context window；主对话只收最终摘要；depth ≤ 5（固定不可配）；maxTurns frontmatter 三档隔离：fresh（从零）/ Explore·Plan（轻量探查跳过 memory）/ fork（继承对话复用 prompt cache）；worktree 物理隔离
D. Auto Mode 独立分类器 model 在动作执行前审查；决策顺序：allow/deny rule → 只读+工作目录放行 → 其余分类器；protected paths 白名单 不可配 fallback：连续 block 3 次 / 累计 20 次 → 暂停恢复人工；对话内 soft boundary 是 block 信号（但 compaction 后会丢）

7. 三 P0 落地（已进入 skill v0.4.0）

三个 P0 扩展全部是纯流程 / prompt 改动，不改 Hermes runtime。已落地到 loop-engineering skill v0.4.0 的 references/dynamic-planning-patterns.md。

7.1 P0-1：动态重 Discovery（Discovery→Verification→重 Discovery 闭环）

目标：把 Discovery 从"一次性 Classify-and-act 路由"升级为"每轮执行后基于 Verification 外部反馈重新评估任务类别"。

触发条件：
  • Verification 评分 < 阈值（默认 0.7，主信号——验证器评分低于阈值触发重路由）
  • 子任务失败（执行结果，非超时）
  • 进度停滞（连续 N 轮无进展，同一路线重试 N 次仍 fail）
安全边界：不可信环境（web 抓取 / 受污染内容）→ 固化为程序，不触发 re-Discovery。重规划预算 max re-Discovery = 3 次，超过则人介入。按失败类型分级（ToolMaze 四分类 + SERF 错误码）：显式瞬时扰动 → 重试；隐式永久扰动 → 重 Discovery；显式永久扰动 → 重 Discovery + 换工具。

来源：CRITIC (arXiv:2305.11738) / LATS (arXiv:2310.04406) / LangGraph Plan-Execute-Replan / Kamoi et al. (TACL 2024)

7.2 P0-2：层次化 Fan-out（dep 字段 + 拓扑调度 + 递归拆解）

目标：把 Fan-out 从"扁平 N 份并行"升级为"递归拆解到原子任务 + 依赖图拓扑调度"。

dep 字段设计： 
delegate_task:
  tasks:
    - id: "extract-data"
      goal: "从 xlsx 提取数据"
      dep: []                    # 无依赖，可立即并行
    - id: "validate-data"
      goal: "验证提取的数据"
      dep: ["extract-data"]      # 等 extract-data 完成后再执行
    - id: "generate-report"
      goal: "生成报告"
      dep: ["validate-data"]     # 等 validate-data 完成后再执行
    - id: "format-chart"
      goal: "格式化图表"
      dep: ["extract-data"]      # 与 validate-data 并行
拓扑调度：构建 DAG → 拓扑排序（入度=0 的 tasks 并行执行）→ 完成后减少依赖者入度 → 循环直到全部完成。递归拆解：子任务可进一步 fan-out，拆解到"原子粒度"（一个原子任务 = 一个可独立验证的产出），拆解层数建议 ≤ 3 层。

不改 delegate_task 实现——主 agent 在调用时声明 dep + 按拓扑序调度。任务树写入文件（非 context），支持跨 session 恢复。

来源：HuggingGPT (NeurIPS 2023) / LangGraph / Conductor / H-RePlan (2026)

7.3 P0-3：ADaPT 式失败→递归分解

目标：把 Loop-until-done 从"失败 → 重试同一路线"升级为"失败 → 递归分解为更细子任务 → 重 Discovery"。+27~33% 成功率（ADaPT 实证）。

流程：子任务失败 → 分析失败原因 → 递归分解（把失败任务拆成 2-3 个更细子任务，例："生成月报"失败 → 拆成"提取数据"+"计算指标"+"格式化"）→ 重 Discovery（对每个子任务重新分类路由）→ 执行子任务。全部成功 → 合成结果；又失败 → 再分解（递归，但受深度限制）。

终止条件：递归深度上限 max = 3 层。层 3 子子任务失败 → 人介入（不再分解）。与 P0-1 联动：每次分解后重 Discovery，重 Discovery 次数也受 max=3 限制。

三 P0 闭环：Discovery → Handoff → Verification → (fail) → ADaPT 分解 → re-Discovery → Handoff。ADaPT = P0-1（重 Discovery）× P0-2（层次化拆解）的交汇。

来源：ADaPT (arXiv:2305.04091) / H-RePlan (2026) / Reflexion (NeurIPS 2023)
不适用场景 ❌ 简单一步任务（分解 / 重路由开销 > 收益）。❌ 不可信环境（web 抓取 / 受污染内容 → 固化为程序，不触发 re-Discovery）。❌ 无可验证 rubric 的开放式创意（无外部反馈信号）。✅ 有可验证交付物 + 多步骤 + 可能失败的长任务。

8. P1 Runtime 设计概要

P1 在 runtime 层（Hermes 核心，不改 messaging 同步 turn 模型）落地三个互相耦合的子系统。状态：只设计，不实施。🟢 设计基于官方来源

8.1 Checkpoint 抽象（BaseCheckpointSaver）

覆盖：缺口 3 子 1 状态持久化 / 子 3 断点恢复。基础来源：Claude Code 支柱 B + LangGraph Checkpointer。

  • 接口：save() 每 user turn 序列化 conversation + file state → load() resume → list() rewind 菜单 → rewind() 四档动作 → queryReversibility() 诚实标注
  • 四档 rewind：restore_all（回代码+对话）/ restore_conversation（只回对话）/ restore_code（只回代码）/ summarize_from · summarize_up（定向摘要）
  • 链式结构：每个 checkpoint 有 parent_checkpoint_id，形成链表（LangGraph time-travel 语义）
  • 诚实标注：bash 副作用（rm/mv/cp/git reset 等）不可逆，rewind 前 queryReversibility() 检查并 warning
  • 集成点：在 delegate_task(background=true) 子 agent 启动时注入 CheckpointSaver；patch/write_file 工具执行前捕获"编辑前快照"

8.2 Context Auto-Compact（ContextManager）

覆盖：缺口 3 子 2 Context 不爆。基础来源：Claude Code 支柱 A + MemGPT 三层 memory。

  • 三层 memory：Working（当前 context window，会爆）/ Recall（历史结构化摘要）/ Archival（外部 SQLite/文件/vector DB，不爆）
  • 触发：getUsageRatio() ≥ autocompact_pct（默认 0.85，env HERMES_AUTOCOMPACT_PCT_OVERRIDE 可覆盖）
  • 保留表：磁盘可重注入（rules/memory/skills）vs message-only 会丢（path-scoped rules）的二元分类
  • Soft constraint 固化：compaction 前把对话内 soft boundary 固化为硬规则（防 goal drift），固化后存磁盘，compaction 后从磁盘重新注入
  • 子 agent 独立：子 agent compaction 不影响主对话 context；transcript 独立持久

覆盖：缺口 3 子 4 无人值守 / 子 5 执行可控性。基础来源：Hermes background subagent + Claude Code 支柱 C/D。

  • 多层级停止：turn 级（max_turns）/ 结构级（max_depth=5）/ 行为级（连续 block 3 / 累计 20 → 暂停）/ 目标级（stop_condition: loop_until_done / goal_satisfied）/ 资源级（token_budget + timeout + auto-compaction）
  • 多事件 callback：completed / failed / progress / checkpoint_saved / compaction_triggered
  • 三设计耦合：Checkpoint × Compact（rewind 的 summarize 调用 compact）；Compact × Guard（soft constraint 固化注入 block_rules）；Checkpoint × Guard（错误 steering 的 replan 调用 rewind）
根本性限制：messaging agent 同步 turn 模型 主 agent 每个 turn 同步，turn 间需要用户消息或 subagent notify 触发。AsyncDelegate 只让子 agent长时运行，主 agent 不能真正 24/7。跨 session resume / 真正 24/7 自治需要架构层 P2（cronjob / daemon 模式）突破。

10. Hermes 架构评估

评估 Hermes 当前架构能支撑 gap map 哪些建议，哪些需要 runtime 层改动。

10.1 能力对照矩阵

gap map 需求当前状态差距落地层
异步执行✅ background=true 已是 async无差距已有
完成通知✅ notify_on_complete无差距已有
并行子任务✅ batch 最多 3 并发无差距已有
subagent 隔离✅ 独立 conversation + terminal无差距已有
Checkpoint❌ 子任务崩溃全丢有差距runtime 层
断点恢复❌ 不能从中间恢复有差距runtime 层
Context auto-compact❌ 单 session context window有差距runtime 层
长时运行（数小时）⚠️ 受 session 生命周期限制有差距runtime 层
Execution guard❌ 无 hooks/limits/steering有差距runtime 层
关键洞察 ⭐ Hermes 的 background subagent 机制已经具备 async delegate 的雏形！background=true + notify_on_complete = 非阻塞 + callback。落地路径比 gap map 预想的更短——不需要从零建 async delegate runtime，只需要在现有 background subagent 机制上加 Checkpoint + Context auto-compact + Execution guard。

10.2 分层结论

层级能做什么需要什么
skill 层（loop-engineering） Discovery 闭环 / Fan-out dep 字段 / ADaPT 式失败分解 改 loop state machine + prompt + 流程设计
runtime 层（Hermes 核心） Checkpoint / Context auto-compact / Execution guard / 跨 session resume 需要改 delegate_task 实现 + 加 checkpoint 后端
架构层（messaging model） 真正 24/7 自治 需要突破同步 turn 模型（cronjob / daemon 模式？）
结论 gap map 的 skill 层 P0 可以立即在 loop-engineering 里落地，不需要等 runtime 改动。runtime 层和架构层是更长期的工作。

11. 落地路线图

1

阶段 1：零新基础设施（P0，1-2 周）

skill 层——不改 Hermes runtime，纯流程 / prompt / 数据结构改动。

  • Discovery 闭环：Verification 评分 → 重 Discovery（改 loop state machine，加 re-Discovery 边）
  • Fan-out dep 字段：子任务声明依赖，按拓扑序调度
  • ADaPT 式失败→递归分解（改 prompt + 流程）
  • 轻量 Checkpoint：delegate step 后序列化 state 到 SQLite

✅ 已落地到 skill v0.4.0

2

阶段 2：层次化 + 异步化（P1，2-4 周）

runtime 层——需要改 Hermes 核心，中等等工程量。

  • Checkpoint 抽象（BaseCheckpointSaver + SQLite 后端 + 四档 rewind）
  • Context auto-compact（三层 memory + 触发阈值 + 保留表）
  • Async delegate 包装现有 background subagent + 多事件 callback
  • ExecutionGuard（limits + hooks）
  • 三档隔离（fresh 已有 / explore / fork）
  • Soft constraint 固化机制（compaction 前固化）

⏳ 只设计，不实施

3

阶段 3：自治 runtime（P2，4-8 周）

架构层——需要突破同步 turn 模型，大工程量。

  • 分级失败恢复（H-RePlan 式）
  • 拆解模板库（HCL-GP / MetaGPT SOP）
  • 多角色 verification loop（planner/implementer/tester）
  • Execution guard 完整版（auto-mode classifier + protected paths）
  • 跨 session resume（cronjob / daemon 模式触发）
  • 真正 24/7 自治

🔮 长期愿景
