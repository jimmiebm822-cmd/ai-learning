1执行摘要

loop-engineering v0.3.1 的五步骤 + 六大模式在验证层已成熟（Adversarial Verification 是核心）， 但三个缺口制约其从"任务内验证循环"外推到"dynamic planning + 长时自治"：

缺口1 · Discovery 静态
Classify-and-act 一次性路由——agent 一开始分类任务就定了路线，执行中即使发现走错路也不重新分类。
缺口2 · Handoff 扁平
Fan-out-and-synthesize 拆 N 份并行，无层次结构、无依赖建模、无动态调整。
缺口3 · Scheduling 同步
Loop-until-done 受单 session 上下文限制，无 checkpoint/resume，不能真正独立运行数小时。
已有 v0.4 方向 vs 本研究
已有 v0.4 候选（Meta-Verifier / Adaptive Rubric / Insight Feed）聚焦验证层进化， 与三缺口正交。本研究扩展到规划层 / 拆解层 / 执行层。
核心论断
三个缺口的共同主题是把 loop 从"单次任务内验证循环"外推到"跨任务 / 跨会话 / 长时的 dynamic planning 闭环"。 统一架构见第 5 节。

2缺口1：Discovery 从静态 → 动态重规划

现状（已验证 SKILL.md L73）

Discovery = Classify-and-act（分类→路由，kanban 分类卡片 + profile 分派）。 一次性路由，执行中即使发现走错路也不重新分类。

Meta-Finding ⭐
纯 LLM 自评的自纠正几乎不奏效（Kamoi et al., TACL 2024）。 真正有效的重规划都依赖外部反馈（环境 / 工具 / 验证器）作为触发信号。

→ Hermes 已有 Verification（Adversarial Verification）步骤 = 天然外部 critic 信号源。

三条核心设计启示

  1. 重规划触发信号必须来自外部 → Discovery→执行→Verification 评分→若低于阈值则重 Discovery。零新基础设施 · 最高 ROI
  2. 失败应触发"重新分解"而非"简单重试"（ADaPT，+27~33% 成功率）→ Loop-until-done 升级为"失败→递归分解→重新 Discovery"
  3. 重规划需有安全边界 → 不可信环境固化为程序；按 ToolMaze 四分类 + SERF 错误码分级处理

未被覆盖的空白

  • 重规划的成本 / 延迟预算控制（何时停止避免无限循环）→ 由 Scheduling 步骤承载
  • 重规划与任务类别分类层的耦合（文献无直接对应，Hermes 独特位置）

方案速查（18 方案 · 高可迁移性 Top-5）

方案触发信号可迁移
LangGraph Plan-Execute-Replan每子任务后执行结果高
CRITIC工具验证后外部工具高
ADaPT子任务失败执行失败高
ReAct每步观察外部观察高
Reflexiontrial 结束语言反馈高
设计启示一句话
把 Verification 的 Adversarial 评分变成 Discovery 的重路由触发信号，闭环就自然形成了——零新基础设施。

3缺口2：Fan-out 从扁平 → 层次化

现状（已验证 SKILL.md L74）

Handoff = Fan-out / Tournament（拆 N 份→并行→合成，delegate_task batch，原生支持）。 扁平一次性拆解，无层次 / 无依赖 / 无动态调整。

Meta-Finding ⭐
LLM 单独规划成功率仅约 3%（LLM Planning Benchmark）→ Fan-out 不能纯靠 LLM 一次性拆解。 大多数方案是两层（planner→executor），真正递归拆解的极少。

推荐迁移路径（优先级排序）

优先级改动来源方案关键点
P0持久化层次任务树Conductor / Deep AgentsFan-out 结果存为持久化树（非 context）
P0依赖图 + 拓扑调度HuggingGPT dep + LangGraph 边子任务声明依赖，按拓扑序执行
P1分级失败恢复H-RePlan（2026 前沿）local 重拆 vs global 重规划
P1递归拆解EvoAgent + LangGraph 子图嵌套递归委托到原子任务
P2拆解模板库HCL-GP 组件库 + MetaGPT SOP从历史成功拆解学习并复用
P2ToT 式回溯Tree of Thoughts子任务失败回溯到父节点

关键洞察

  • 两层不够，需要递归——大多数方案停在 planner→executor，真正递归拆解的是前沿
  • 外部化是前提——任务树持久化到外部非 context，与 Persistence 步骤契合
  • 分级恢复是关键创新——H-RePlan 2026 前沿，局部重拆 vs 全局重规划
  • 学习并复用拆解——HCL-GP 组件库思路

4缺口3：同步 delegate → 长时自治 runtime

现状（已验证 SKILL.md L77）

Scheduling = Loop Until Done。delegate_task 同步阻塞， 受单 session 上下文限制，无 checkpoint / resume。

5 大子缺口 + 对应方案

#子缺口现状业界方案迁移路径
1状态持久化delegate 临时调用，崩溃全丢LangGraph Checkpointer, MAF, TemporalBaseCheckpointSaver 抽象，每 step 序列化到 SQLite/文件
2Context 不爆单 session context window 限制MemGPT, Claude Code auto-compaction三层 memory（working/recall/archival）+ auto-compact
3断点恢复不能从中间恢复Claude Code checkpoint+rewind, LangGraph time-travel每 step checkpoint，支持 resume + rewind
4无人值守主 agent 阻塞等待Claude Code auto mode, OpenHands Agent ServerAsync delegate（非阻塞 + callback/event）
5执行可控性无限制 / 错误恢复Strands hooks, Anthropic stopping conditionsHooks + limits + steering + adversarial review
关键实战案例 ⭐
long-running-coding-loop — 全自治 implement-test-fix 循环， 12 小时连续运行，11/11 功能完成，$181 成本，0 人工干预。
四阶段：PLAN→IMPLEMENT→COMPILE→TEST→FAIL则FIX。多角色分离（planner / implementer / tester 各在独立 context）。

→ 这是 Hermes Loop-until-done 的直接实战验证。

推荐的 Hermes Async Delegate 架构

delegate_task(task_spec) → AsyncDelegate
  ├─ CheckpointManager   # SQLite/文件，每 step 序列化
  ├─ ContextManager      # working/recall/archival 三层 + auto-compact
  ├─ ExecutionGuard      # hooks/limits/steering/auto-mode classifier
  └─ VerificationLoop    # planner→implementer→tester，loop until pass
       └─ callback → 主 Agent  # 非阻塞通知

关键设计决策

  1. 不引入完整 Temporal server（太重）→ Hermes 内部轻量 checkpoint + retry
  2. 借鉴 Claude Code harness 模式（auto-compaction + checkpoint + subagent isolation + auto mode）
  3. MemGPT 三层 memory作为 context 管理框架
  4. long-running-coding-loop 多角色分离作为 verification loop 模板
  5. Strands hooks + steering作为执行可控性基础设施

4.5Claude Code Harness 四支柱工程实现

Phase 3 深挖 Anthropic 官方文档 + blog。Harness = 包裹 loop 的全部控制逻辑——context 管理、checkpoint、subagent 编排、权限、停止条件。Dynamic workflows = Claude 运行时自己写出 harness（JS 脚本），把 harness 变成 agent 可自编排的产物。

四支柱速查

支柱核心机制关键工程细节Hermes 迁移启示
A. Auto-Compaction 接近 context limit 自动 summarize 阈值可控（env var）；保留表区分"磁盘可重注入"vs"message-only 会丢"；子 agent compaction 独立于主 区分两类状态；规则/记忆存磁盘能重载；带条件的规则会随 compaction 丢失
B. Checkpoint/Rewind 每 user prompt = 一个 checkpoint 四档 rewind：回代码+对话 / 回对话 / 回代码 / 定向摘要；bash 副作用不可逆；fork 分支保留原路径 每 user turn 一快照；四档动作而非单一 undo；明确标注 bash 不可逆边界
C. Subagent Isolation 独立 context window + 自定义 prompt 三档隔离：fresh / Explore+Plan 轻量 / fork 复用 cache；worktree 物理隔离；depth≤5；transcript 独立于主 compaction 对话历史隔离+配置共享；三档隔离强度；transcript 独立防"压缩丢子 agent 工作"
D. Auto Mode 独立分类器 model 审动作 决策顺序：allow/deny→只读放行→分类器；对话内 soft boundary（compaction 会丢→需固化）；三层子 agent 检查；fallback 3连续/20累计 独立分类器；soft constraint 在 compaction 前固化为硬规则；不可配 fallback 阈值

多层级停止条件（防无限循环）

层级机制
Turn 级maxTurns frontmatter（子 agent）
结构级depth limit = 5（固定不可配）
行为级block 连续 3 次 / 累计 20 次 → 暂停恢复人工
目标级/goal 硬完成要求 + loop-until-done stop condition
资源级token budget + auto-compaction
⭐ 关键洞察：对话内 soft boundary（如"don't push"）会因 compaction 丢失 → Hermes 若做"对话内 soft constraint"，必须在 compaction 前固化为硬规则或纳入 system prompt 重注入层，否则 goal drift。

7Hermes 架构可行性评估

Phase 3 产出。评估 Hermes 当前架构能支撑 gap map 哪些建议，哪些需要 runtime 层改动。

当前 delegate_task 机制

机制描述
同步模式不设 background → 阻塞等待子任务返回，在主 session turn 内执行
background 模式background=true → 立即返回 delegation_id，子任务异步执行，完成时 notify_on_complete 重新注入消息
batch 模式tasks 数组，最多 3 个并发（max_concurrent_children=3）
嵌套限制max_spawn_depth=1（leaf 不能再 delegate；orchestrator 被强制为 leaf）
子 agent 隔离独立 conversation + terminal session + toolset，无主 agent memory
通知background subagent 完成时，full result 重新注入为 new message

能力对照矩阵

gap map 需求当前状态差距落地层
异步执行✅ background=true 已是 async无差距已有
完成通知✅ notify_on_complete无差距已有
并行子任务✅ batch 最多 3 并发无差距已有
subagent 隔离✅ 独立 conversation + terminal无差距已有
Checkpoint❌ 子任务崩溃全丢有差距runtime 层
断点恢复❌ 不能从中间恢复有差距runtime 层
Context auto-compact❌ 单 session context window有差距runtime 层
长时运行（数小时）⚠️ 受 session 生命周期限制有差距runtime 层
Execution guard❌ 无 hooks/limits/steering有差距runtime 层
关键洞察 ⭐
Hermes 的 background subagent 机制已经具备 async delegate 的雏形！
background=true + notify_on_complete = 非阻塞 + callback。 这正是缺口3 P0 "Async delegate + callback" 需要的核心。

落地路径比 gap map 预想的更短——不需要从零建 async delegate runtime，只需要在现有 background subagent 机制上加： Checkpoint · Context auto-compact · Execution guard。

分层结论

Skill 层（loop-engineering） 低工程量 · 可立即做
能做：Discovery 闭环 / Fan-out dep 字段 / ADaPT 式失败分解
需要：改 loop state machine + prompt + 流程设计
Runtime 层（Hermes 核心） 中等等工程量
能做：Checkpoint / Context auto-compact / Execution guard / 跨 session resume
需要：改 delegate_task 实现 + 加 checkpoint 后端
架构层（messaging model） 大工程量 · 长期
能做：真正 24/7 自治
需要：突破同步 turn 模型（cronjob / daemon 模式？）
结论
gap map 的 skill 层 P0 可以立即在 loop-engineering 里落地，不需要等 runtime 改动。 runtime 层和架构层是更长期的工作。

8路线图建议（三阶段）

阶段1：零新基础设施（P0） 1-2 周 · skill 层
  • Discovery 闭环：Verification 评分 → 重 Discovery（改 loop state machine，加 re-Discovery 边）
  • Fan-out dep 字段：子任务声明依赖，按拓扑序调度
  • 轻量 Checkpoint：delegate step 后序列化 state 到 SQLite
阶段2：层次化 + 异步化（P1） 2-4 周 · skill + runtime 层
  • ADaPT 式失败→递归分解
  • 持久化任务树（外部化）
  • Async delegate + callback（基于已有 background 机制）
  • Context auto-compact（三层 memory）
阶段3：自治 runtime（P2） 4-8 周 · runtime + 架构层
  • 分级失败恢复（H-RePlan 式）
  • 拆解模板库（HCL-GP / MetaGPT SOP）
  • 多角色 verification loop（planner / implementer / tester）
  • Execution guard（hooks / limits / steering）
